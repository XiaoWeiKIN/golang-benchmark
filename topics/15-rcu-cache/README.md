# 15 · 读多写少的并发缓存：RCU + 攒批合并

同样是"只读一张 map"，并发度从 1 涨到 10：

```
map + RWMutex     7.10 ns  →  85.45 ns      塌了 12 倍
不可变快照        6.71 ns  →   2.38 ns      反而快了 2.8 倍
```

**读锁并不是"免费的读"。** 这个专题讲清楚三件事：那 12 倍是怎么来的、
不可变快照怎么绕开它、以及为什么快照必须**攒批**发布（不攒批的话写入是 O(N²)）。

```bash
make bench TOPIC=15-rcu-cache
go test -bench 'Read_' -cpu=1,2,4,10 ./topics/15-rcu-cache   # 看并发度扫描
go test -v -run 'TestH4|TestH5' ./topics/15-rcu-cache        # 内存尖峰和 GC 回收
```

## 这个模式是什么

两半，用的是两个不同的技术：

**读侧 —— RCU（Read-Copy-Update）**

```go
snapshot atomic.Pointer[map[string]int]   // 发布后永不修改

func (c *Cache) Get(k string) (int, bool) {
    v, ok := (*c.snapshot.Load())[k]       // 一次原子加载 + 一次 map 查找
    return v, ok
}
```

快路径上**一个写操作都没有**。要改就构造新的一份、原子换指针；旧读者手里那份继续有效。

**写侧 —— 攒批合并（LSM 式的 memtable → immutable table）**

```go
func (c *Cache) Put(k string, v int) {
    c.mu.Lock()
    c.pending[k] = v
    c.writes++
    if c.writes > uint64(len(*c.snapshot.Load())) {   // ← 自适应阈值
        c.mergeLocked()
        c.writes = 0
    }
    c.mu.Unlock()
}
```

新 key 先进有锁的小表，攒够了才整体合并进快照。

> **这个组合不是什么冷门技巧 —— Go 老版本的 `sync.Map` 内部用的就是它**：
> `read`（原子只读）+ `dirty`（有锁）+ `misses` 计数，`misses > len(dirty)` 时提升。
> VictoriaMetrics 的字符串驻留表（[专题 04](../04-strings/#场景-6五种实现怎么选)）
> 也是同一套，只是去掉了 `any` 装箱。
>
> **而 Go 1.24 把 `sync.Map` 换成了 HashTrieMap，放弃了这个设计。**
> 场景 6 会给出为什么。

## 场景 1：读锁为什么在多核上会塌

只读，表里 1024 个 key 全部命中，用 `-cpu=1,2,4,10` 扫并发度：

| 并发度 | `map`+`RWMutex` | 分片 map | 1→10 |
|---:|---:|---:|---|
| 1 | 7.10 ns | 12.81 ns | |
| 2 | 24.59 ns | 12.93 ns | |
| 4 | 33.73 ns | 15.82 ns | |
| 10 | **85.45 ns** | 23.67 ns | **12.0× / 1.85×** |

**为什么。** `RLock` 不是"什么都不做"，它要**原子递增一个共享的读计数器**。
单线程时这条指令几乎免费；10 个核同时做时，那个计数器所在的 cache line
在核之间来回弹（cache line ping-pong），每次弹都是一次跨核同步。

**读多写少并不能让 `RWMutex` 免疫竞争** —— 因为读本身就在写那个计数器。

分片把这条线拆成 16 条，好了很多（1.85× vs 12×），但**没有根治**：
每个分片内部还是同一个计数器。

> **只信两端的数字。** 这批数据的噪声地板（两个函数体逐字相同的实现）
> 在 1 核是 9.9%、10 核是 0.1%，但**2 核和 4 核高达 30% 和 46%**。
> 中间两档的具体数值不可信，只有 1→10 的趋势是结实的。见坑三。

## 场景 2：不可变快照与原子发布

| 并发度 | 不可变快照 | `map`+`RWMutex` |
|---:|---:|---:|
| 1 | 6.71 ns | 7.10 ns |
| 2 | 3.80 ns | 24.59 ns |
| 4 | 2.55 ns | 33.73 ns |
| 10 | **2.38 ns** | 85.45 ns |

**并发度越高越快。** 这不是笔误 —— 10 核时每次操作 2.38 ns，比单核的 6.71 ns
**快 2.8 倍**。

**为什么。** `atomic.Load` 读一个几乎从不改变的指针，各核的 cache 里都有它的
共享副本（MESI 的 Shared 状态），**读它不需要任何跨核通信**。map 本身也是只读的。
于是 10 个 goroutine 完全并行，吞吐随核数增长，摊到每次操作的时间就下降了。

理想的线性加速应该是 6.71/10 = 0.67 ns，实测 2.38 ns —— 达到理想值的 28%，
剩下的受内存带宽和 map 查找本身限制。

**怎么用。** 判断一个并发数据结构会不会塌，看**读路径上有没有写**：

| 读路径上的动作 | 会不会塌 |
|---|---|
| `atomic.Load` 一个稳定的指针 | 不会，各核共享缓存 |
| `atomic.Add` 一个计数器（`RLock`） | 会，cache line 弹跳 |
| 加互斥锁 | 会，而且更严重 |

## 场景 3：为什么必须攒批

读侧已经最优了，代价全在写侧。如果**每次写都复制整张表**：

| n | 插入 n 个 key 的总耗时 | 相对 n=1000 |
|---:|---:|---:|
| 1,000 | 10.15 ms | 1× |
| 3,000 | 97.70 ms | 9.6×（n 涨 3 倍） |
| 10,000 | 1.322 s | 130×（n 涨 10 倍） |

**这是标准的 O(N²)** —— n 涨 3 倍耗时涨 9 倍，n 涨 10 倍涨 100 倍（实测 130，
n=10000 那一格只跑了一两次迭代，±97%，量级可信、精度不可信）。

道理很直白：每插入一个 key 都复制一次 N 个条目，插入 N 个就是 N×N。

**所以"copy-on-write"这个叫法是有害的** —— 它字面上就是"每次写都复制"，
而那正是行不通的做法。真正让它可用的是**攒批**：

| n | 攒批合并 | 每 key |
|---:|---:|---:|
| 10,000 | 1.622 ms | 162 ns |
| 100,000 | 19.27 ms | 193 ns |

n 涨 10 倍，总耗时涨 11.9 倍 —— **线性**，每 key 的平均成本基本恒定。

## 场景 4：阈值为什么要自适应

`c.writes > uint64(len(*c.snapshot.Load()))` 这行看着随意，其实是整个设计的支点。
换成固定阈值 K=1000 试试：

| n | 自适应阈值 | 固定 K=1000 | 差距 |
|---:|---:|---:|---:|
| 10,000 | 1.622 ms | 1.887 ms | 1.16× |
| 100,000 | **19.27 ms** | **174.2 ms** | **9.0×** |

n 涨 10 倍：**自适应涨 11.9 倍（线性），固定涨 92 倍（接近二次）。**

**为什么。** 表有 N 个条目、每 K 次写合并一次，插入 N 个 key 要合并 N/K 次，
每次 O(N) → 总成本 **O(N²/K)**。固定阈值只是把二次项的常数缩小了 K 倍，
**没有改变复杂度**。

自适应阈值让"合并间隔"随表一起增长：表有 N 个条目就要攒 N 次写才合并，
于是总合并成本是 N + 2N + 4N... 的等比数列，摊还到每次写是 **O(1)**。

**怎么用。** 自己实现这类结构时，**合并/重建的触发条件必须和当前规模挂钩**。
写成"每 1000 次"、"每 10 秒"这种固定值，表小的时候没事，表大了就退化。

## 场景 5：合并的两个代价

### 代价一：内存尖峰 —— 但没有想象中大

合并瞬间新旧两份快照并存。事前预测总堆会出现 ≥1.8× 的尖峰，**实测只有 1.4 倍**：

```
n=100000   稳态 8320 KB → 合并后 11733 KB（总堆 1.41×）→ GC 后 8320 KB
           其中 key 字符串+切片 4886 KB，map 自身 3433 KB
           合并多出来 3413 KB —— 正好是 map 自身的 0.99×
```

**机制是对的，我把量算错了。** 被复制的只有 **map 结构本身**，
key 字符串和 value 都是共享的，一个字节都不复制。这里 key 占了总堆的 60%，
所以总堆的尖峰被稀释成 1.4 倍。

**实践含义比原假说更有用**：尖峰的绝对值 ≈ map 结构自身的大小。
value 越大、key 越长，尖峰占总内存的比例反而越小。真正危险的是
**大量小 key/小 value 的表** —— 那时 map 结构占比高，尖峰接近 2 倍。

### 代价二：旧快照什么时候被回收

传统 RCU 最麻烦的一步是"什么时候能安全回收旧版本"，要显式等所有读者退出临界区
（grace period）。**Go 里 GC 替你做了**：

```
场景一（没人持有旧快照）：旧快照已回收 ✅
场景二（读者还持有引用）：旧快照未回收 ✅
```

（用 `runtime.SetFinalizer` 观察，两轮 `runtime.GC()` 之后检查。）

读者拿到的是解引用后的 map 值，只要它还在栈上，旧 map 就不会被回收；
一旦最后一个读者放手，下一轮 GC 就收走。**语义正好是 RCU 需要的，而且不用写一行同步代码。**

代价是回收时机不可控 —— 如果有长命的读者一直持有旧快照，旧版本会一直积压。

## 场景 6：什么时候不该用它

前面全是读多写少。把写掺进去，10 核并发：

| 写比例 | RCU+攒批 | `sync.Map`（Go 1.24） | 分片 map | `map`+`RWMutex` |
|---:|---:|---:|---:|---:|
| 0% | **3.40 ns** | 3.85 ns | 23.06 ns | 88.64 ns |
| 1% | 6.62 ns | **5.03 ns** | 27.41 ns | 32.66 ns |
| 5% | 18.12 ns | **7.57 ns** | 29.28 ns | 24.70 ns |
| 20% | 52.56 ns | **14.83 ns** | 34.73 ns | 27.93 ns |
| 50% | 102.7 ns | **27.82 ns** | 37.80 ns | 58.51 ns |

噪声地板 ≤1.5%，所以这些差距全是真的。

**交叉点在 0% 和 1% 之间。** 事前预测是 5% 附近 —— **猜大了至少 5 倍**。
只要有 **1%** 的写，`sync.Map` 就已经反超；到 5% 已经领先 2.4 倍；
到 20% 时 RCU+攒批连 `RWMutex` 都不如。

**为什么。** 每次写都要拿全局那把锁，而且周期性触发 O(N) 的整体合并。
写比例一上来，"读侧零成本"省下的那点时间根本填不上写侧的坑。

**这大概就是 Go 1.24 换掉 `sync.Map` 的原因。** 老实现（read/dirty/misses）
在读多写少时很好，但一旦有持续写入，dirty 提升的 O(N) 拷贝就成了瓶颈。
HashTrieMap 用无锁的哈希前缀树，读依然接近无锁，**写不需要周期性的全量重建** ——
从上表看，它在每个写比例下都稳定，这才是通用容器该有的样子。

> **一个没解释清的观察**：`RWMutex` 是**非单调**的 —— 0% 时最差（88.64 ns），
> 5% 时反而最好（24.70 ns），50% 又变差（58.51 ns）。这个 U 形在两批数据里都复现了。
> 我的猜测是写锁让读者排队，反而降低了读计数器的争用频率，但**没有验证**，
> 别把它当结论。

## 结论：选型

| 你的场景 | 选 |
|---|---|
| **近乎纯读**（写 <1%），且要极致读性能 | **RCU + 攒批合并** |
| 需要按业务窗口整体丢弃/重建整张表 | 同上（快照可以直接换掉） |
| 有持续写入（≥1%） | **`sync.Map`**（Go 1.24+ 的 HashTrieMap） |
| 写为主 | `sync.Map` 或分片 map |
| 单线程 / 低并发 | `map` + `RWMutex`，代码最短 |
| 只是想存不可变的字符串 | `unique.Make`，见[专题 04](../04-strings/#结论什么时候该用驻留) |

**自己实现 RCU+攒批时的三条硬要求：**

1. **合并阈值必须和规模挂钩**（场景 4），固定值会退化成 O(N²)；
2. **读路径上不能有任何写**，包括看起来无害的计数器（场景 1）；
3. **算一下内存尖峰**：≈ map 结构自身的大小（场景 5）。

## 一页速查

| 看到这样的代码 | 想一下 |
|---|---|
| 读路径上有 `RLock` / `atomic.Add` | 多核下会塌，考虑换不可变快照 |
| `atomic.Pointer` + 每次写重建整张表 | O(N²)，必须攒批 |
| 合并/重建条件写成"每 K 次"或"每 T 秒" | 表大了会退化，改成和 `len()` 挂钩 |
| 用 RCU 存写比例 >1% 的数据 | 换 `sync.Map` |
| 担心旧快照泄漏 | GC 会收，但长命读者会拖住它 |
| 把这个模式叫 "copy-on-write" | 字面意思正是行不通的做法，见场景 3 |

## 三个坑

### 坑一：把"被复制的东西"和"总量"搞混

事前预测合并会让**堆**出现 ≥1.8× 尖峰，实测 1.4×。

机制没错 —— 合并多出来的字节精确等于 **map 自身的 0.99×**。错在我算的是总堆，
而 key 字符串占了 60% 且完全不参与复制。

> **教训**：预测一个"翻倍"时，先问清楚**什么翻倍**。
> 这次是 map 结构翻倍，不是内存占用翻倍。差别在于分母。

### 坑二：交叉点猜大了 5 倍

预测 RCU+攒批在 5% 写比例附近才输给 `sync.Map`，实测**在 1% 就已经输了**。

我高估了"读侧零成本"能补偿多少写侧开销。实际上写侧的全局锁 + 周期性 O(N) 合并
太贵，读侧那点优势（3.40 vs 3.85 ns）几乎立刻被吃掉。

> **教训**：两个方案在各自擅长的维度上差距是不对称的。这里读侧只差 13%，
> 写侧差几十倍 —— **交叉点会紧贴着弱势那一边**，而不是落在中间。

### 坑三：中等并发度的测量最不稳

噪声地板（两个函数体逐字相同的实现）随并发度剧烈变化：

| 并发度 | 1 | 2 | 4 | 10 |
|---|---:|---:|---:|---:|
| 噪声地板 | 9.9% | **30%** | **46%** | 0.1% |

1 核和 10 核都很稳，**中间两档完全不可信**。猜测是 2/4 个 goroutine 时
调度器把它们放在哪些核上（P 核还是 E 核、共不共享 L2）影响巨大，
而 10 核时所有核都用上了，反而没有这个自由度 —— 但**没有验证**。

> **教训**：并发扫描要**同时报每一档的噪声地板**，别默认它是个常数。
> 本专题所有跨并发度的结论都只用 1 和 10 两端。

| | 假说 | 结果 |
|---|---|---|
| H1 | `RLock` 的代价是 cache line 争用：1→10 核 `RWMutex` 涨 ≥10×，RCU 涨 <2× | ✅ **命中且超预期** —— `RWMutex` 涨 12.0×，RCU 反而**降到 0.35×** |
| H2 | 纯 RCU 写入是 O(N²)，n 涨 10 倍耗时涨约 100 倍 | ✅ 命中（涨 130×） |
| H3 | 自适应阈值必要：K=1000 时 n=1e5 慢 ≥3× | ✅ 命中（慢 **9.0×**，且随 n 拉开） |
| H4 | 合并瞬间总堆 ≥1.8× 尖峰 | ❌ **被推翻**（1.41×）—— 机制对、量算错，见坑一 |
| H5 | GC 替 RCU 做 grace period | ✅ **两个场景全中**（本轮置信度最低的一条） |
| H6 | 写比例交叉点在 5% 附近 | ⚠️ **方向对，阈值猜大 5 倍** —— 实测在 1% 以下，见坑二 |

**H1 的"超预期"值得单独说**：我预测 RCU 读"上升 <2 倍"，实际是**下降到 0.35 倍**。
方向对（不恶化），但我没想到它会随并发度**改善** —— 那是完美并行的标志，
per-op 时间随核数下降。预测写成"上升"本身就暴露了我默认"并发只会让事情变糟"。

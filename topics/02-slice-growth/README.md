# 02 · slice 扩容：append 的容量是怎么长起来的

往一个 slice 里塞 1000 个 `int`，加一句预分配：

```go
var s []int                  // 1.678 µs   24.6 KiB   12 allocs
s := make([]int, 0, n)       // 0.733 µs    8.0 KiB    1 alloc
```

**分配次数 12 → 1，字节数少了三分之二。** 这个专题讲清楚那 12 次是怎么来的、
省下的到底是什么，以及什么时候预分配反而是负担。

```bash
make bench TOPIC=02-slice-growth                     # 跑基准
go test -v -run TestGrowthCurve ./topics/02-slice-growth   # 打印容量序列
```

## 扩容策略：两步走

`append` 发现 cap 不够时调用 `growslice`，容量按两步算出来。

**第一步，`nextslicecap` 决定要多少**（`runtime/slice.go`）：

```go
const threshold = 256
if oldCap < threshold {
    return doublecap            // 小切片直接翻倍
}
for {
    newcap += (newcap + 3*threshold) >> 2   // 大切片逐步逼近 1.25 倍
    if uint(newcap) >= uint(newLen) { break }
}
```

**第二步，`roundupsize` 把字节数向上取整到 size class。** 你要 6656 字节，
分配器只有 6784 这一档，多出来的 128 字节顺手变成额外容量。

两步合起来，实测的容量序列（`go test -v -run TestGrowthCurve`）：

```
[]byte : 8  16  32  64  128  256  512  896  1408  2048  3072  4096  5376
[]int  : 1   2   4   8   16   32   64  128   256   512   848  1280  1792  2560  3408  5120
```

拿 `[]int` 手算验一遍：`512 → 512 + (512+768)/4 = 832` 个元素 = 6656 字节，
取整到 6784 字节 = **848** 个元素 ✅。再一轮 `848 + (848+768)/4 = 1252` = 10016 字节，
取整到 10240 = **1280** ✅。整条序列都对得上。

**要记住的三件事：**

1. **翻倍的拐点是 256 个元素，不是 1024。** Go 1.18 改的，网上大量文章还停留在 1024。
2. **拐点算的是元素个数，不是字节数。** `[]byte` 和 `[]int` 都在 256 个元素处转向。
3. **超过拐点后不是精确的 1.25 倍**，而是 `+= (n + 768)/4`，再被 size class 抬一点，
   实测比值在 1.31~1.75 之间波动，随规模变大才趋近 1.25。

> **一个容易被 `cap()` 骗到的地方**：`make([]int, 0, 100)` 的 `cap()` 报 **100**，
> 但实际占了 **896 字节**（100×8=800，取整到 896）。`makeslice` 不把多出来的空间
> 算进 cap，但内存已经花掉了。**`cap` 看不见的浪费也是浪费。**

## 场景 1：预分配省下了什么

```go
//go:noinline
func AppendNoPrealloc(n int) []int {
	var s []int                       // ← 唯一的差异
	for i := range n { s = append(s, i) }
	return s
}

//go:noinline
func AppendPrealloc(n int) []int {
	s := make([]int, 0, n)            // ← 唯一的差异
	for i := range n { s = append(s, i) }
	return s
}
```

| n | 不预分配 | 预分配 | 快了 |
|---:|---|---|---:|
| 10 | 68.46 ns / 248 B / **5 allocs** | 14.83 ns / 80 B / **1 alloc** | 4.6× |
| 100 | 223.5 ns / 1992 B / **8 allocs** | 83.33 ns / 896 B / **1 alloc** | 2.7× |
| 1000 | 1.678 µs / 24.6 KiB / **12 allocs** | 732.9 ns / 8.0 KiB / **1 alloc** | 2.3× |
| 10000 | 20.20 µs / 349 KiB / **19 allocs** | 5.844 µs / 80 KiB / **1 alloc** | 3.5× |

**为什么。** 分配次数就是容量序列的长度：长到 1000 个 `int` 要经过
`1,2,4,…,512,848,1280` 共 12 档，每档一次 `mallocgc` 加一次 `memmove`。
24.6 KiB 是**历次旧数组的总和**（1+2+4+…+848+1280 = 3151 个元素 × 8 = 25208 字节），
其中 17 KiB 立刻变成垃圾。

所以预分配省下的是三样：11 次分配、约 17 KiB 的垃圾、以及累计约 3000 个元素的拷贝。

**怎么用。** 只要**能估出上界**就预分配 —— 哪怕估得不准。从 map 转 slice、
从数据库结果集拼列表、按已知长度过滤，这些地方 `len` 是现成的：

```go
out := make([]Item, 0, len(in))     // 一行的事
for _, v := range in {
    if keep(v) { out = append(out, v) }
}
```

估多了浪费的是内存（见场景 5），估少了也只是退回到原来的扩容路径，**不会更差**。

## 场景 2：预分配之后，append 还是索引

预分配之后，这两种写法哪个快？

```go
s := make([]int, 0, n)                  // A：append
for i := range n { s = append(s, i) }

s := make([]int, n)                     // B：索引
for i := range n { s[i] = i }
```

| n | append | 索引 | 差距 |
|---:|---|---|---:|
| 10 | 14.79 ns | 15.00 ns | 1.4% |
| 100 | 82.97 ns | 83.53 ns | 0.7% |
| 1000 | 723.9 ns | 715.3 ns | 1.2% |
| 10000 | 5.494 µs | 5.438 µs | 1.0% |

`B/op` 和 `allocs/op` 四档全部一模一样。

**这个差距是零。** 判断依据不是"1% 很小"，而是这台机器上有个现成的噪声地板：
`AppendPrealloc` 和 `FillByAppend` 两个函数**函数体逐字相同**，分别测出
5.844 µs 和 5.494 µs —— **6.4%**。既然完全相同的代码都能差 6.4%，
1% 就不是信号。

**为什么没差距。** cap 足够时，`append` 编译出来就是"写一个元素 + `len++`"，
没有函数调用，`growslice` 那条分支不会走到。索引版省掉的 `len++` 是一条寄存器加法，
在内存写入面前可以忽略。

**怎么用。** **按可读性选，不按性能选。**

- 数量确定、要按下标随机填 → `make([]T, n)` + 索引
- 边过滤边收集、数量不确定 → `make([]T, 0, n)` + append

顺带一个真正的坑：`make([]T, n)` 之后再 `append` 会追加到 **第 n+1 个位置**，
不是覆盖前面 —— 这是长度和容量搞混时最常见的 bug，和性能无关。

## 场景 3：元素里有没有指针

同样追加 n 个 8 字节元素，只换元素类型：

| n | `[]int` | `[]*int` | 慢了 |
|---:|---|---|---:|
| 10 | 75.27 ns / 5 allocs | 86.52 ns / 5 allocs | 1.15× |
| 100 | 229.8 ns / 8 allocs | 342.6 ns / 8 allocs | 1.49× |
| 1000 | 1.771 µs / **12 allocs** | 2.240 µs / **11 allocs** | 1.26× |
| 10000 | 22.89 µs / **19 allocs** | 46.62 µs / **18 allocs** | 2.04× |

指针版**更慢，但分配次数更少**。两件事，分开说。

**慢是意料之中**：`growslice` 搬运含指针的数据要走带写屏障的拷贝，而且这块内存
之后每轮 GC 都要被扫描。规模越大差距越明显 —— n=10000 时已经 2 倍。

**分配次数更少是意料之外的。** 看容量序列：

```
[]int  : … 64  128  256  512  848  1280
[]*int : … 64  143  287  607  1023
```

143、287、607、1023 全是奇数。各自 ×8 再 **+8**，正好落在 size class 上：
1152、2304、4864、8192。

多出来的 8 字节是 **malloc header**（Go 1.22 引入）。`runtime/msize.go`：

```go
func roundupsize(size uintptr, noscan bool) (reqSize uintptr) {
	reqSize = size
	if reqSize <= maxSmallSize-gc.MallocHeaderSize {
		if !noscan && reqSize > gc.MinSizeForMallocHeader {
			reqSize += gc.MallocHeaderSize          // 含指针且 >512 字节：先加 8
		}
		...SizeClassToSize[...] - (reqSize - size)  // 取 size class，再把 8 减回去
	}
	...
}
```

`MallocHeaderSize = 8`、`MinSizeForMallocHeader = 8 × 64 = 512` 字节。
含指针的对象要在开头留 8 字节存类型指针，所以可用容量是 `sizeclass - 8`。
分歧点正好出现在 `[]*int` 首次超过 512 字节那一步（64 个元素 = 512 字节，
下一步要 1024 字节 → 触发 header）。

**怎么用。**

- 装指针、字符串、interface、含指针字段的结构体时，**预分配的收益比装纯数值时更大**；
- 大量小对象考虑改成 `[]T` 而不是 `[]*T` —— 少一层间接，GC 也不用扫；
- 别用 `cap()` 去反推分配器给了多少内存，含指针时对不上。

## 场景 4：批量 append

```go
for _, v := range src { s = append(s, v) }    // 逐个
s = append(s, src...)                          // 批量
```

| n | 逐个 | 批量 | 快了 |
|---:|---|---|---:|
| 10 | 84.50 ns / **5 allocs** | 15.99 ns / **1 alloc** | 5.3× |
| 100 | 293.0 ns / **8 allocs** | 71.63 ns / **1 alloc** | 4.1× |
| 1000 | 1.787 µs / **12 allocs** | 601.6 ns / **1 alloc** | 3.0× |
| 10000 | 22.69 µs / **19 allocs** | 3.833 µs / **1 alloc** | 5.9× |

**为什么。** `append(s, src...)` 一次就知道最终需要多少，`nextslicecap` 里
`newLen > doublecap` 直接返回 `newLen`，一次扩容到位。逐个 append 每次只知道
"再多一个"，只能一档一档往上爬。

批量版还额外省下了循环本身：底层是一次 `memmove`，不是 n 次单元素写入。

**怎么用。** 合并切片时永远写 `append(dst, src...)`，别写循环。
`copy(dst[i:], src)` 在 dst 已经有空间时更直接。

## 场景 5：预分配过头

`len` 固定 10 个元素，只改预分配的 `cap`：

| cap | ns/op | B/op | 实际用到 |
|---:|---|---:|---|
| 10 | 15.12 ns | 80 | 80 B |
| 100 | 87.62 ns | 896 | 80 B |
| 1000 | 552.9 ns | 8192 | 80 B |
| 10000 | 3.271 µs | 81920 | 80 B |

**同样是放 10 个元素，慢了 216 倍。**

**为什么。** `make` 出来的内存要清零，清零成本跟 `cap` 走，不跟 `len` 走。
而且这块内存全程占着，GC 扫描时也按 cap 算。**决定成本的是 cap，不是 len。**

**怎么用。** 两个真实场景：

1. **别拍脑袋预分配一个大数**。`make([]T, 0, 10000)` "以防万一"，
   在只放 10 个元素时是净亏损。估不出上界就别预分配，让 `growslice` 去爬。

2. **小心从大 slice 切出小 slice**：

   ```go
   big := readAll()          // 1 MB
   small := big[:10]         // 底层数组还是那 1 MB，整块都回收不了
   small = slices.Clip(small) // 或 append([]T(nil), big[:10]...)
   ```

   `slices.Clip` 把 cap 砍到 len，但**不会**复制 —— 底层数组依然是原来那块。
   真要释放，得拷贝出来。这是 Go 里最经典的内存泄漏之一。

## 一页速查

| 场景 | 怎么写 |
|---|---|
| 知道上界 | `make([]T, 0, n)`，一行换掉 O(log n) 次分配 |
| 估不出上界 | 别预分配，让 growslice 去爬，别拍一个大数 |
| 合并两个切片 | `append(dst, src...)`，不要写循环 |
| 预分配后填充 | append 和索引一样快，按可读性选 |
| 元素含指针 | 预分配收益更大；能用 `[]T` 就别用 `[]*T` |
| 从大切片留一小段 | 拷贝出来，`slices.Clip` 不释放底层数组 |
| 想知道实际占了多少 | 别信 `cap()`，`cap` 之外还有 size class 取整 |

## 三个坑

### 坑一：不逃逸的 slice 有个 32 字节的栈上缓冲区

第一版 `TestGrowthCurve` 测出来的序列是：

```
[]byte : 32  64  128  256 …          ← 8 和 16 去哪了
[]int  :  4   8   16   32 …          ← 1 和 2 去哪了
```

两个开头都是 **32 字节**。因为被观察的 slice 没有逃逸，编译器给了它一个
32 字节的栈上缓冲区，前几次 append 根本没碰堆。加一句 `sink = s` 强制逃逸后，
才是真序列 `[8 16 32 …]` / `[1 2 4 …]`。

> **教训**：观察 runtime 行为时，先确认被观察的对象真的在 runtime 手里。
> 一个不逃逸的 slice 和线上代码里的 slice 不是一回事。

### 坑二：实验设计不对，机制没错也测不出来

事前写下的预测（H1′）：

> `cap(make([]byte, 0, 100))` == 100，而让 `append` 自然长到能装下 100 字节时，
> `cap` 会是 112（size class）。

前半命中，**后半测出来是 128**。但机制没错 —— 问题在于逐个 append 是从 64
**翻倍**到 128，压根没机会去"凑" 100，所以看不到取整。换成一次性要 100 字节：

```go
var b []byte
b = append(b, make([]byte, 100)...)    // cap = 112 ✅
```

`roundupsize` 一直在那儿，是我的测法没把它隔离出来。

> **教训**：预测落空时先问"我的实验真的在测这个变量吗"，再怀疑机制。
> 这和坑一不同 —— 坑一是测了个不存在的东西，这里是测了个**别的**东西。

### 坑三：先量噪声地板，再谈差异

场景 2 里 append 和索引差 1%。这算差距吗？

`AppendPrealloc` 和 `FillByAppend` 两个函数**函数体逐字相同**，
分别测出 **5.844 µs 和 5.494 µs —— 差 6.4%**。

既然完全相同的代码都能差 6.4%，1% 显然是噪声。

这个对照组本来是写重复了，留下来当噪声地板反而最有用 ——
它比 benchstat 的置信区间更直观：后者说的是同一个基准自身的波动，
前者说的是**两个不同基准之间多大的差值才算真的不同**。

这条已经写进 [METHODOLOGY.md 原则 6](../../METHODOLOGY.md)，
从本专题起每个专题都要留一对。

> load average 一度到 286。采集时 load 稳定在 5~7。

## 附录 B：假说与实验设计

六条假说在跑任何基准之前写定，原文保留在 `slice_test.go` 开头，未做修改。

| | 假说 | 结果 |
|---|---|---|
| H1 | 拐点 256、`newcap += (newcap+3*256)/4`、再 roundupsize | ✅ 完全命中，源码逐字对上 |
| H1′ | makeslice 不取整、growslice 取整到 112 | ⚠️ 前半命中；后半**测法失败**，见坑二 |
| H2 | 预分配把 O(log n) 次分配压成 1 次 | ✅ 命中（1000 → 12 变 1，预测区间 10–20） |
| H3 | 分配行为相同，索引版略快但在 2 倍以内 | ✅ 分配部分完全命中；**"索引版略快"没观察到**，1% 落在噪声里 |
| H4 | `[]*T` 的 ns 至少是 `[]int` 的 1.5 倍，allocs 相同 | ❌ **两处都被推翻**，见下 |
| H5 | 批量 append 只扩容一次 | ✅ 命中 |
| H6 | cap 而非 len 决定内存和耗时 | ✅ 命中（216× 差距） |

**H4 被推翻的两处：**

1. **"allocs 相同"错了** —— `[]*int` 反而更少（11 vs 12）。原因是 malloc header
   改变了容量序列，我的假说里只想到它影响拷贝方式和 GC 扫描，没想到影响容量本身。
2. **"至少 1.5 倍"在 n=1000 处没达到** —— 实测 1.26×。方向对，幅度错：
   n=100 时 1.49×、n=1000 时 1.26×、n=10000 才到 2.04×。写死一个倍数是个坏预测，
   应该预测"随规模单调上升"。

**控制变量：**

| 场景 | 变量 | 控住什么 |
|---|---|---|
| 增长曲线 | 观察不计时 | 强制逃逸，绕开栈缓冲区 |
| 1 | 是否预分配 | 元素类型、数量、循环体完全一致 |
| 2 | append vs 索引 | 都预分配到 n，写入的值相同 |
| 3 | `int` vs `*int` | 都是 8 字节元素；源数据在计时外准备好 |
| 4 | 批量 vs 逐个 | 源数据、目标初始状态一致 |
| 5 | 预分配的 cap | `len` 固定为 10 |
| — | **噪声地板** | 两个函数体逐字相同的对照组 |

四档规模 10/100/1000/10000 全跑，因为增长曲线的结论在小规模上可能不成立 ——
事实证明确实如此，H4 的倍数就随规模单调变化。

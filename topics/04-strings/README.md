# 04 · 字符串：拷贝、零拷贝与驻留

一个 `string` 值是两部分：**16 字节的头**（数据指针 + 长度）+ 一段只读**数据**。

```
s := "go1.16.4"

  s ──► ┌──────────┬────────┐
        │ data ptr │ len=8  │   16 字节，在栈上或内嵌在容器里
        └────┬─────┴────────┘
             ▼
        ┌──────────────────┐
        │ "go1.16.4"       │   8 字节，堆上的独立对象
        └──────────────────┘
```

这一个事实决定了本专题的两半：**转换的成本在于要不要复制数据**，
**驻留的收益上限在于数据能被多少个头共享 —— 而头本身省不掉。**

```bash
make bench TOPIC=04-strings
go test -v -run 'TestH4|TestH7|TestH8' ./topics/04-strings   # 内存和 GC 的观察
```

# 上半场：转换什么时候拷贝

## 场景 1：默认转换要拷贝

`string` 不可变，`[]byte` 可变，所以两个方向的转换默认都要复制数据。

| 长度 | `string(b)` | `[]byte(s)` |
|---:|---|---|
| 16 | 8.31 ns / 16 B / 1 alloc | 9.48 ns / 16 B / 1 alloc |
| 64 | 10.26 ns / 64 B / 1 alloc | 11.49 ns / 64 B / 1 alloc |
| 256 | 21.99 ns / 256 B / 1 alloc | 23.07 ns / 256 B / 1 alloc |

**为什么。** 汇编里能直接看到那次拷贝：

```asm
BytesToString:  CALL runtime.slicebytetostring(SB)
```

`B/op` 和长度严丝合缝 —— 16/64/256 都恰好是 size class，没有取整损耗。

**怎么用。** 这是本专题的基线。下面两节讲怎么让这次拷贝**不发生**。

## 场景 2：真正的规则是逃不逃逸

网上流传一份"零拷贝特例清单"：`m[string(b)]`、`string(b) == "字面量"`、
`for range string(b)`、`append(b, s...)`。实测这四种确实都是 0 分配：

| 写法 | ns/op | allocs/op |
|---|---:|---:|
| `LookupTable[string(b)]` | 5.53 | **0** |
| `string(b) == "go1.16.4"` | 1.74 | **0** |
| `for range string(b)` | 4.55 | **0** |
| `append(dst, s...)` | 1.75 | **0** |

**但这份清单是错的 —— 或者说，它描述的是一条更一般规则的几个特例。**

我原本预测：把 `string(b)` 存进中间变量就会破坏特例，变成 1 次分配。

```go
func LookupViaVar(b []byte) int {
	s := string(b)          // ← 我以为这里会拷贝
	return LookupTable[s]
}
```

实测 **0 分配**。换成 40 字节的长 key（排除"短串走栈缓冲区"的猜测），**还是 0 分配**。

汇编给出答案 —— 根本没有转换这回事：

```asm
BytesToString:      CALL runtime.slicebytetostring   ←  真拷贝
LookupDirect:       CALL runtime.mapaccess1_faststr  ←  只有查表
LookupViaVar:       CALL runtime.mapaccess1_faststr  ←  只有查表，中间变量不影响
LookupViaVarLong:   CALL runtime.mapaccess1_faststr  ←  40 字节也一样
```

逃逸分析把话说得更明白：

```
strings.go:25:53: string(b) escapes to heap        ← BytesToString，要拷贝
strings.go:45:61: string(b) does not escape        ← LookupDirect
strings.go:52:14: string(b) does not escape        ← LookupViaVar
```

**规则只有一条：`string(b)` 的结果如果不逃逸，编译器就让它的头直接指向 `b` 的底层数组，零拷贝；一旦逃逸，才调 `slicebytetostring` 真复制。**

那四个"特例"之所以零拷贝，是因为在那些位置转换结果**证明得出不会逃逸**，
而不是因为编译器认得那四种语法。

**怎么用。**

- 别背清单，去问编译器：`go build -gcflags='-m' ./pkg`，看那行 `string(b)` 是 `escapes to heap` 还是 `does not escape`；
- 只要转换结果不被返回、不存进外部结构、不进 `any`，怎么写都零拷贝；
- 反过来，**只要它要逃逸，写成 `m[string(b)]` 也救不了**。

> 这条和[专题 01](../01-escape-analysis/) 是同一件事的两面：那边讲对象凭什么留在栈上，
> 这边讲转换凭什么不拷贝 —— 判据都是逃逸分析。

## 场景 3：unsafe 零拷贝，代价是不可变性

真的必须零拷贝、但结果又要逃逸时，只剩 `unsafe`：

```go
func UnsafeString(b []byte) string {
	return unsafe.String(unsafe.SliceData(b), len(b))
}
```

| 长度 | `string(b)` | `unsafe.String` |
|---:|---|---|
| 16 | 8.31 ns / 1 alloc | **1.774 ns / 0 alloc** |
| 64 | 10.26 ns / 1 alloc | **1.773 ns / 0 alloc** |
| 256 | 21.99 ns / 1 alloc | **1.773 ns / 0 alloc** |

耗时和长度**完全无关**（1.773/1.773/1.774）—— 它只是造了个 16 字节的头，没碰数据。

**代价是 Go 里最基本的一条不变量没了：string 不再不可变。**

```go
b := []byte("hello")
safe := string(b)                                       // 拷贝
unsafeS := unsafe.String(unsafe.SliceData(b), len(b))   // 共享底层数组

b[0] = 'J'
// safe   == "hello"
// unsafeS == "Jello"   ← 一个 string 的内容被改掉了
```

**怎么用。** 只在满足全部三条时才用：

1. 转换后**绝不再修改**那个 `[]byte`；
2. 那个 `[]byte` 的生命周期**覆盖** string 的生命周期；
3. 这段代码在热路径上，且你已经用 profile 证明了这次拷贝确实是瓶颈。

反方向的 `unsafe.Slice(unsafe.StringData(s), len(s))` 更危险 —— 字符串字面量在只读段，
写进去直接段错误。

# 下半场：驻留

驻留（string interning）就是让重复的字符串共用同一份数据：

```go
var table = map[string]string{}

func intern(s string) string {
	if v, ok := table[s]; ok { return v }
	table[s] = s
	return s
}
```

典型场景是监控系统：成千上万个 target 上报同一批 label 串（`{version="go1.16.4"}`），
同一份数据在内存里躺着几万个副本。日志系统的字段名、协议解析里的 header 名、
数据库的列名，都是同一类问题。

下面四节回答四个问题：**能省多少、省的是什么、用什么实现、对 GC 有什么影响。**

## 场景 4：驻留省下的到底是什么

很自然的直觉是：三份变一份，就省 3 倍；一万份变一份，就省一万倍。

**不是这样。** 回到开头那张图 —— 每个引用仍然要占 16 字节的 string 头，
驻留只能让它们共享**数据**那一段：

```
不驻留 ≈ n × (16 + len)          驻留 ≈ n × 16 + k × len
节省倍数 ≈ (16 + len) / 16       ← 只跟字符串长度有关，跟重复次数无关
```

实测（`n` 个引用指向同一个长度 `len` 的串，测的是**存活堆**不是 `B/op`）：

| n | len=16 | len=64 | len=256 |
|---:|---:|---:|---:|
| 100 | 1.68× | 3.97× | 13.27× |
| 1000 | 1.94× | 4.80× | 16.35× |
| 10000 | 1.97× | 4.90× | 16.60× |
| **公式预测** | **2.00×** | **5.00×** | **17.00×** |

**重复次数从 100 涨到 10000（100 倍），节省倍数纹丝不动**（4.80 → 4.90）。
n 越大越贴近公式，因为驻留表本身的固定开销被摊薄了。

**怎么用。**

- **先算一下再决定**：`(16+len)/16`。你的字符串平均多长？
  - 16 字节的短串 → 最多省 2 倍，多半不值得为它维护一张表；
  - 64 字节 → 省 5 倍，开始有意义；
  - 256 字节以上 → 省 17 倍，很划算。
- **重复度不影响节省倍数，只影响绝对节省量。** 重复度决定"值不值得建这张表"，
  长度决定"每个引用能省多少"。
- 想省掉那 16 字节的头？只有换数据结构 —— 比如用 `uint32` 的 ID 索引一张字符串表。

## 场景 5：驻留不是吞吐优化

我原本预测："命中率低于某个阈值（猜 50%）驻留会变成净亏损。"

**实测：驻留在所有命中率下都更慢、更费内存。阈值不是 50%，是 100%。**

每个 op 处理 10000 个 key，命中率由这批里有多少个不同的 key 决定：

| 命中率 | 驻留 | 不驻留 |
|---|---|---|
| 99.9% | 187.6 µs / 626 KiB | **117.9 µs / 625 KiB** |
| 90% | 267.6 µs / 782 KiB | **118.0 µs / 625 KiB** |
| 50% | 470.6 µs / 1.23 MiB | **119.2 µs / 625 KiB** |
| 0% | 754.4 µs / 1.86 MiB | **127.3 µs / 625 KiB** |

**为什么。** 想清楚就很显然：要查表，你**必须先有那个字符串** —— 那次解析和分配
一次都省不掉。驻留是在这之上**再加**一次哈希查表，未命中还要再加一次插入。

**热路径上，驻留永远是净增开销。它的收益 100% 在存活内存（场景 4），不在吞吐。**

> **一个常见误解**：以为驻留能省掉解析时的那次分配。省不掉 —— 驻留只是让临时那份
> 尽快变成垃圾，而不是让它不产生。真想连这次分配都省掉，那是场景 2 的活。

**怎么用。**

- 判断该不该驻留，看的是**存活内存**曲线，不是 benchmark 的 `ns/op` 或 `B/op`；
- 重复度低的数据别驻留 —— 0% 命中时慢 5.9 倍，内存还多花 3 倍（表里全是废条目）；
- 真想连解析分配都省掉，那是场景 2 的活（让转换结果不逃逸），不是驻留的活。

## 场景 6：五种实现怎么选

命中路径，五种实现签名一致 `Intern(string) string`：

| | 单线程 | 并发·单热点 key | 并发·1024 key | allocs/op |
|---|---:|---:|---:|---:|
| `map` + `RWMutex` | **6.47 ns** | 85.66 ns | 85.03 ns | **0** |
| 16 分片 `map` | 9.35 ns | 82.75 ns | 24.32 ns | **0** |
| `sync.Map`（`LoadOrStore(s, s)`） | 27.05 ns | 14.97 ns | 22.27 ns | **2** |
| `unique.Make` | 14.88 ns | 5.26 ns | 7.24 ns | **0** |
| **双 map + 原子发布** | 6.78 ns | **1.84 ns** | **5.34 ns** | **0** |
| *噪声地板* | *6.34（2.0%）* | *88.14（2.9%）* | *91.67（7.8%）* | |

### 单锁在多核上会塌

从 6.47 ns 恶化到 85.66 ns，**13 倍**。哪怕只是 `RLock`，那个共享计数器也在核间来回弹
cache line —— **读多写少并不能让 `RWMutex` 免疫竞争**。

分片把这条线拆成 16 条，分散 key 下好了 3.5 倍（24.32 ns）；但**单热点 key 下毫无改善**
（82.75 ns）—— 同一个 key 永远哈希到同一个分片，16 把锁退化成 1 把。

### `sync.Map` 的写法有个陷阱：每次命中都分配 32 B / 2 allocs

```go
interned, _ := m.LoadOrStore(s, s)   // LoadOrStore(key, value any)
```

```
strings.go:171:33: s escapes to heap    ← 第一个实参装箱
strings.go:171:36: s escapes to heap    ← 第二个实参装箱
```

形参是 `any`，实参 `string` 必须装箱，**装箱发生在调用点，跟命不命中无关**。
缓存命中率 100% 也照样分配两个 16 字节的头。

一个以**减少分配和 GC 压力**为目的的技术，却在每次查询时制造新垃圾。
这正是[场景 2](#场景-2真正的规则是逃不逃逸) 那条规则的反面：
**`any` 强制逃逸，编译器的零拷贝路径被堵死了。**

### 最快的那个，靠的是把"写"从快路径上赶走

并发下最快的是双 map 方案（VictoriaMetrics 的
[`lib/bytesutil/internstring.go`](https://github.com/VictoriaMetrics/VictoriaMetrics/blob/master/lib/bytesutil/internstring.go)
用的就是这个设计）：

```go
type VMInterner struct {
    mutableLock  sync.Mutex
    mutable      map[string]string                    // 有锁，攒新 key
    mutableReads uint64
    readonly     atomic.Pointer[map[string]vmEntry]   // 不可变，原子发布
}

func (m *VMInterner) Intern(s string) string {
    readonly := m.getReadonly()
    if e, ok := readonly[s]; ok {
        return e.s        // 快路径：一次 atomic.Load + 一次 map 查找
    }
    // ... 慢路径：加锁、Clone、写 mutable、攒够了整体迁移
}
```

这个结构值得拆成两半看，因为**两半用的是两个不同的技术**。

**读侧是 RCU（Read-Copy-Update）。** readonly 一旦发布就永不修改；要改就构造新的一份、
原子换指针；旧读者手里那份继续有效。快路径上**一个写操作都没有**，多核并行读它不产生
任何写共享，所以没有 cache line 弹跳 —— 这是它比 `RWMutex`（`RLock` 要原子递增读计数）
和分片方案（每片内部仍有竞争）快的根本原因，也是它能比 `unique.Make` 还快的原因
（后者要算哈希、查内部表、构造 `Handle`、再解引用）。

传统 RCU 最麻烦的一步是"什么时候能安全回收旧版本"，要显式等所有读者退出临界区。
**这里 GC 替它做了**：读者解引用拿到的 map 值还在栈上，旧 map 就不会被回收 ——
Go 里实现 RCU 比 C 里省一大半心思。

**写侧是攒批合并，这才是设计的关键。** 新 key 先进有锁的 `mutable`，
攒够 `len(readonly)` 次慢路径才整体合并进 readonly。

这一步常被简单叫作 "copy-on-write"，但那个叫法既不准确、也盖住了重点：
**如果真按字面每写一次就复制一次，插入 N 个 key 就是 O(N²)。** 攒批把 O(N) 的
全量拷贝摊薄成 O(1)（下一节有实测）。整个结构更接近 **LSM 的 memtable → immutable table**：
可变的小表接收写入，按阈值整体 flush 进不可变的大表。

两个容易被忽略但很关键的细节：

**1. 插入时的 `strings.Clone` 不是可有可无的。**

```go
sInterned = strings.Clone(s)   // 切断对可能更大的源字符串的引用
m.mutable[sInterned] = sInterned
```

从 1 MB 解析缓冲区里切出的 20 字节 label，如果直接存进表，会把整个 1 MB
**永久钉在内存里** —— 驻留表本来要省内存，反而成了泄漏源。这和
[专题 02 的 `slices.Clip` 坑](../02-slice-growth/#场景-5预分配过头)是同一类问题的字符串版本。

**2. 查询路径可以零分配地接受 `[]byte`。**

```go
func InternBytes(b []byte) string {
    s := ToUnsafeString(b)   // 零拷贝，只为查表
    return InternString(s)
}
```

用 unsafe 转换**只做查询**，命中就返回表里那份；未命中才在锁内 `Clone`。
这是[场景 2](#场景-2真正的规则是逃不逃逸)和[场景 3](#场景-3unsafe-零拷贝代价是不可变性)
组合起来的正确用法 —— 而 `sync.Map` 因为要过 `any`，**根本做不到这一点**。

### 快路径的优势，插入时要还回去

前面的表全是命中路径。往一张空表里插入 n 个互不相同的 key（全部未命中）：

| n | 双 map（每 key） | `map`+`RWMutex`（每 key） |
|---:|---:|---:|
| 1,000 | 163.4 ns | 77.6 ns |
| 10,000 | 186.6 ns | 77.0 ns |
| 100,000 | 179.6 ns | 76.3 ns |

**插入贵 2.3 倍** —— 多了一次 `strings.Clone`、一次加锁、外加周期性的全量迁移。

但**迁移的摊还成本确实是 O(1)**：n 涨 100 倍（1e3 → 1e5），每 key 平均耗时只在
163~187 ns 之间波动（1.14 倍）。触发条件 `mutableReads > len(readonly)` 保证了
readonly 有 N 个条目时要攒够 N 次慢路径才迁移一次，所以 O(N) 的拷贝被摊薄成常数。

设计上还有个代价这批数据没测：**合并的瞬间，新旧两份 readonly map 同时存在**，
表很大时会出现约 2× 的内存尖峰。

### 选型

| 你的情况 | 选 |
|---|---|
| Go 1.23+，不需要控制驻留表生命周期 | **`unique.Make`** —— 标准库，弱指针自动回收 |
| 需要按业务窗口/TTL 整体丢弃驻留表 | **双 map + 原子发布** —— 最快，但要自己维护 ~150 行 |
| 想暴露 flag 给运维调（最大长度、过期时间、开关） | 同上 |
| 单线程或低并发，代码要短 | `map` + `RWMutex` 够用 |
| 任何情况 | **别用 `sync.Map` 存 string** |

## 场景 7：驻留对 GC 的影响

20 万个引用指向同一个 64 字节的串：

```
不驻留   单轮 GC 1.614 ms   HeapAlloc 15831 KB   存活对象 200398
驻留     单轮 GC 0.972 ms   HeapAlloc  3332 KB   存活对象    402
```

**GC 快了 1.66 倍，存活对象少了 498 倍。**

我事前给这条假说写了个反面理由，结果**反面理由是错的**：

> 字符串数据是 noscan 的，GC 不扫内容只扫 header 指针，而 header 数量并没有减少 ——
> 所以很可能测不出差别。

漏掉的一点：**string 头是内嵌在 `[]string` 切片里的，不是独立堆对象**。
20 万个独立堆对象是那 20 万块**数据**，驻留后只剩 1 块。GC 的标记成本跟**对象数量**
强相关（每个对象都要定位 span、置标记位、判断要不要扫描），而不只是跟"要扫描的指针数"相关。
我把"GC 不扫内容"错当成了"GC 不管这些对象"。

> **一个诚实的保留**：这个实验里对象数（200398 → 402）和堆大小（15.8 MB → 3.3 MB）
> 是**一起变的**，所以"GC 变快主要归因于对象数"还需要一个能把两者分开的实验才能坐实。
> 现在能确定的是"驻留让 GC 变快"，机制归因还欠一步。

## 结论：什么时候该用驻留

**字符串驻留是拿吞吐换存活内存的技术。它不会让代码更快，只会让内存占用更小 ——
而且省的只是数据那一段，每个引用的 16 字节头一分钱都省不掉。**

| | |
|---|---|
| ✅ 降低**存活内存** | 倍数 = `(16+len)/16`：1.97×(16B) / 4.90×(64B) / 16.60×(256B) |
| ✅ 降低 **GC 成本** | 存活对象数 20 万 → 402，单轮 GC 快 1.66× |
| ❌ 不降低**分配流量** | 要查表就得先有那个字符串，那次解析分配一次都省不掉 |
| ❌ 不提高**吞吐** | 99.9% 命中仍慢 1.6×，0% 命中慢 5.9× |

### 该用：两个条件要同时满足

**一、字符串够长** —— 长度决定节省倍数：

| 平均长度 | 16 B | 32 B | 64 B | 128 B | 256 B+ |
|---|---:|---:|---:|---:|---:|
| 节省倍数 | 2× | 3× | 5× | 9× | 17× |
| 判断 | 不值当 | 边缘 | 有意义 | 划算 | 很划算 |

**二、重复度够高** —— 重复度决定节省的绝对量。不同值的数量 `k` 要远小于引用数 `n`；
`k/n` 接近 1 就是纯亏损，表里堆满只用一次的条目，内存反而多花 3 倍。

典型场景：**监控 label 串、日志字段名、协议 header 名、数据库列名、租户标识** ——
共同特征是**取值空间小、出现次数大、单个值不短**。

### 不该用

- **想让代码变快** —— 方向错了，该看[场景 2](#场景-2真正的规则是逃不逃逸)
- **短串**（< 32 字节）—— 省不下什么，还多一次哈希
- **高基数数据**（用户 ID、trace ID、时间戳）—— 几乎全是未命中，表还会无限膨胀
- **没测过内存曲线** —— 这是内存指标驱动的优化，拍脑袋上没有意义

### 实现怎么选

Go 1.23+ 直接用标准库：

```go
import "unique"

h := unique.Make(s)   // Handle[string]，可比较、可作 map key
s2 := h.Value()
```

需要**按业务窗口整体丢弃驻留表**、或者要暴露 flag 给运维调时，才自己写 ——
用双 map + 原子发布（并发 1.84 ns / 0 分配，比 `unique` 还快），别用分片 map。
**任何情况下都别用 `sync.Map` 存 string** —— 见[场景 6](#场景-6五种实现怎么选)。

### 决策清单

```
平均长度 < 32 字节？                    → 别用
不同值的数量 ≈ 总引用数？               → 别用
只是想让代码变快？                      → 别用，方向错了
存活内存是真实瓶颈 + 长串 + 高重复？
    ├─ Go 1.23+                        → unique.Make
    └─ 需要手动控制表的生命周期          → 分片 map
```

## 一页速查

**转换**

| 你要做的 | 怎么写 |
|---|---|
| 转换结果不逃逸（查表、比较、range、append） | 随便写，编译器零拷贝 |
| 不确定会不会拷贝 | `go build -gcflags='-m'` 看那行是不是 `does not escape` |
| 结果要逃逸但必须零拷贝 | `unsafe.String`，且保证之后不改原 `[]byte` |
| 想靠 `m[string(b)]` 这类"技巧"省分配 | 先确认它本来就不逃逸 —— 要逃逸的话这招没用 |

**驻留**（该不该用见[上一节](#结论什么时候该用驻留)，这里只列代码层面的）

| 看到这样的代码 | 怎么改 |
|---|---|
| `m.LoadOrStore(s, s)` 做驻留 | 每次调用 2 allocs，换 `unique.Make` |
| 自己写 `map` + 一把全局锁 | 多核下会塌，换 `unique` 或分片 |
| 自己实现驻留表的 TTL / 轮换 | Go 1.23+ 交给 `unique` 的弱指针 |
| 用 benchmark 的 `B/op` 论证驻留有效 | 指标选错了，看 `HeapAlloc` |
| 用 `cap()` / `len()` 估驻留省了多少 | 别忘了每个引用还有 16 字节的头 |

## 五个坑

### 坑一：把"特例清单"当成了规则

我事前预测"存进中间变量会破坏零拷贝特例"，实测 0 分配；换 40 字节长 key 想验证
"短串走栈缓冲区"的猜测，**还是 0 分配，第二个猜测也错了**。

两次都错在同一个地方：**我在猜语法，而编译器看的是逃逸。**
第三次不猜了，直接看汇编 —— `LookupViaVar` 里压根没有 `slicebytetostring` 这个调用。

> **教训**：`-gcflags='-m'` 和 `-S` 就在手边，两次猜测的时间够看三次汇编了。
> 遇到"为什么没分配/为什么分配了"，**第一反应应该是去看，不是去想**。

### 坑二：并发基准里所有 goroutine 打同一个 key

第一版并发基准让 10 个 goroutine 反复 intern 同一个 key，测出分片 map（88.84 ns）
和单锁 map（83.67 ns）**一样慢**，看起来像是"分片没用"。

当然没用 —— 同一个 key 永远哈希到同一个分片，16 个锁退化成 1 个。
换成 1024 个分散的 key 重测，分片版 22.51 ns，是单锁的 **4 倍快**。

> **教训**：测并发数据结构时，**key 的分布本身就是被测变量**。
> 单点热 key 和均匀分布是两个完全不同的场景，别用其中一个的结论去说另一个。

### 坑三：`B/op` 回答不了"省不省内存"

场景 4 和场景 5 得出方向相反的结论，因为它们量的是两个东西：

- `B/op` 是**分配流量** —— 驻留让它变差（多一次查表、未命中还要插入）；
- `HeapAlloc` 是**存活内存** —— 驻留让它好 2~17 倍。

驻留是拿吞吐换存活内存。**只看 benchmark 的 `B/op`，会得出"驻留没用"的结论；
只看内存曲线，会得出"驻留免费"的结论。两个都要看。**

### 坑四：两边能不能重置，本身就是个变量

事前预测："全未命中时，双 map 方案会慢于 `unique`"（每次未命中它都要 `Clone` +
加锁 + 可能迁移，而 `unique` 只需在自己表里插一次）。

每 op 处理 10000 个 key：

| 命中率 | 双 map | `unique` | |
|---|---:|---:|---|
| 99.9% | **242.9 µs** | 288.3 µs | 双 map 快 19% |
| 90% | 432.1 µs | **386.3 µs** | `unique` 快 12% |
| 50% | 1.068 ms | **1.003 ms** | `unique` 快 6% |
| 0% | **1.818 ms** | 16.65 ms | 双 map 快 **9.2 倍** |

交叉点确实存在（落在 99.9% 和 90% 之间），但 **0% 那一格的方向和预测完全相反**。

原因不在实现，在实验：**双 map 每批新建一张表**（对应 TTL 到期后重建），
**而 `unique` 是全局的，用户没法重置** —— 它的表在整个 `b.N` 期间持续累积唯一串，
只能等 GC 回收，而回收跟不上产生速度。两边做的工作量根本不一样。

这个不对称**不是纯粹的实验缺陷**，它反映了一个真实的属性差异：可轮换的表能整体丢弃，
`unique` 不能。但正因为工作量不对称，**那个 9.2 倍不能读成"双 map 快 9 倍"**。

> **教训**：对比两个数据结构时，**"能不能主动清空"本身就是一个变量**。
> 如果一边能重置而另一边不能，就别把它们放进同一张耗时表 —— 要么把这个差异作为
> 被测对象单独设计实验，要么只比较双方都能做到的操作。
>
> 能带走的结论只有定性的那半句：**持续产生唯一字符串的负载下，
> 可轮换的表是个真实优势**。量化它需要另一个对称的设计。

### 坑五：噪声地板会随场景变化

本专题量到三个不同的地板（都是函数体逐字相同的一对）：

| 场景 | 噪声地板 |
|---|---:|
| 单线程 ~7 ns 的操作 | **13%** |
| 并发·单热点 key | 0.02% |
| 并发·1024 key | 1.1% |

单线程那 13% 明显偏大 —— 操作只有 7 ns，测量开销占比高。所以场景 6 里
"单锁 7.15 ns vs 分片 10.88 ns" 是真差距（52%），但如果两者差 10%，
在这批数据里就该判定为无差别。

> **教训**：地板不是一个专题一个数，是**一批数据一个数**。
> 量级差很多的基准放在一起时，尤其要小心。
